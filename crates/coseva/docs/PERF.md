# What coseva costs

Generated by `scripts/perf_report.rs` from the normalized machine-readable
artifact produced by `scripts/perf_artifacts.py`. Do not edit by hand.

## Read throughput

Callgrind instruction counts: instructions retired reading a whole document,
divided by the number of records in it. They are reproducible to the
instruction, which is what makes a 2% difference meaningful rather than noise.

They are not times. Instruction counts do not model cache misses, branch
misprediction or memory bandwidth, and a document large enough to fall out of L2
is not modelled well by any of them. Read them as a strong signal about how much
work is done and a weak one about wall clock.

Both crates get an 8 KiB buffer and are asked to resolve headers, so no
comparison here is secretly a comparison of buffer sizes or header settings.
Every case asserts a checksum computed by the document generator rather than by
a parse, so a case that skipped a column or stopped unescaping fails instead of
reporting a better number; `tests/benchmark_parity.rs` runs those same
assertions without valgrind.

## Paths the `csv` crate cannot express

Two of the five shapes have no counterpart in `csv`: it has no borrowed record
form, and no typed decoding of its own beyond Serde. Those are reasons to reach
for this crate that a head-to-head instruction count cannot show, so what they
cost relative to the shapes that *do* have a counterpart is worth stating
directly.

## Where the differences come from

The spread across documents is wide enough to be worth accounting for. Each of
these was read off a profile, not inferred from the table.

**Long fields are where the gap is largest.** On `prose`, whose free-text column
runs to a few hundred bytes, `csv` spends about 89% of its time inside
`csv_core`'s reader, which advances one byte at a time through a state machine —
roughly eleven instructions for every input byte. This crate locates the closing
quote with a vector search and copies the field with one `memcpy`, so its cost
per byte is several times lower. The longer the fields, the further those two
diverge; a document of short fields would not show it.

**Many short columns are where it is narrowest.** On `wide`, at 128 columns, the
work is dominated by per-field bookkeeping — a boundary, a bounds check, a push —
which neither crate can vectorise away, and there is little field body over which
to amortise a scan. The two converge to within a few per cent there, and that is
the honest worst case for this crate.

**The typed rows diverge for a different reason.** `csv` has no typed decoding of
its own, so its Serde path assembles a record first and deserializes out of it;
this crate decodes from the parsed field spans without materialising the record
in between. That is a structural difference rather than a faster loop, which is
why the deserialized rows move further than the record rows do.

**Borrowing is worth more the wider the record.** `Record` hands back fields that
point into the input, so a wide record costs no allocation, where an owned record
pays for one per field. That is the largest single difference in the capability
table above, and it is available only on `SliceParser` and inside a `PushParser`
chunk, where the input outlives the record.

Two follow-up probes on 2026-08-15 used the same 64 MiB document shape with
`CARGO_TARGET_DIR=target-perf-parallel`. They were diagnostic wall-clock runs,
not baseline refreshes. The first temporarily timed the borrowed `fold` path's
serial boundary pass and parallel phase separately for 15 repetitions. The
boundary pass was roughly constant in absolute time and became a larger share
as more workers shortened the parallel phase:

| Threads | Total `fold` median | Boundary median | Parallel phase median | Boundary share |
|---:|---:|---:|---:|---:|
| 2 | 61.0 ms | 15.8 ms | 44.4 ms | 25.9% |
| 4 | 41.0 ms | 18.1 ms | 23.9 ms | 44.2% |
| 8 | 28.3 ms | 15.7 ms | 12.9 ms | 55.5% |
| auto | 27.7 ms | 15.5 ms | 12.5 ms | 56.0% |

The serial borrowed median in the same run was 79.3 ms, so the boundary pass is
not immaterial: because the serial path does not run it at all, the prelude by

published reference row's serial time gives the same conclusion at roughly a
4× cap. Past eight threads the already-minimal boundary scan is therefore the
majority of elapsed time and a real hard ceiling, but it does not explain the
remaining gap between the measured 2-3× speedup and that 4-5× ceiling. That
gap remains bandwidth and coordination. A speculative parallel boundary scan
is still not recommended without stronger evidence: it would have to reconcile
quote parity across chunk boundaries for hostile quoted input while preserving
the exact split and deterministic-error contracts.

## Allocation and peak memory

The focused harness instruments the process global allocator over generated
numeric documents. Peak memory below means **peak additional live heap**, not
resident set size; input and harness setup are outside the measured region.

The parallel rows run at a pinned four threads, because the pools they watch are
sized per worker and a row taken at the host's thread count could not be
committed. Each parallel path is measured at 16 MiB and at 64 MiB: the pair is
the only way to state what `parallel.rs` promises — that peak follows the
threads and their work unit and not the document — and the harness fails when
either grows more than threefold for the fourfold document. `index_build_serial`
runs below the parallel index threshold so it stays the serial builder whatever
the host has, and `index_build_parallel` is the threaded one beside it.

## How to read the measurements

- Callgrind sections are deterministic work counts, not elapsed time.
- Parallel and proc-macro sections are wall-clock measurements and are meaningful
  only on the host named in their evidence block.
- Peak heap excludes the generated input and is not operating-system RSS.
- Every corpus is synthetic. Measure your own data when its shape differs.
- Instruction counts from different benchmark binaries are not comparable to each
  other; the optimizer's inlining decisions inside a measured loop depend on the
  rest of the binary. Every ratio quoted anywhere in this crate is between rows
  measured in one binary.
- Source comments justifying an `#[inline]` with a percentage record what removing
  it measured at the time. They are observations, not enforced properties: a gate
  can only measure the code as written, never the counterfactual. The properties
  that are enforced are the ratios listed by `scripts/perf_gate.py`.

The normalized artifact is publication evidence: generation refuses a dirty tree,
records each section's exact command, host, toolchain and revision, and fails if
any focused harness is absent rather than printing a placeholder.
